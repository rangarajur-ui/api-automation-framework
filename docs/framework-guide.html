Shared guide for product, QA, and anyone new to this repo

A guest scans a QR, pays, and the kitchen gets a real order. These tests prove that path end to end.

This is not a mock. On a pass, someone at the table could have paid on Telr, the cart became an accepted order, and the back-office OMS shows the same items, totals, guest name, and item notes.

Product: what “done” means Fresher QA: which file starts first Non-tech: same story, two restaurants

What we automate

Dine-in QR Order & Pay on Paytm Checkout. Scan code → menu → cart → Telr card page → paid order → OMS confirmation.

What a PASS means

Payment status is payment_success, order status is order_accepted, OMS matches the cart, and notes sit on the line item — not on the whole order.

What we never store in Git

Card number, CVV, OMS session tokens, slip URLs. Those stay on the machine or in Jenkins. Reports mask mobiles (last 4 only).

1. The guest journey — and where the test finishes

Click a step. The same seven steps run on the test restaurant and the staging restaurant. The finish is step 7: OMS back office, not “payment URL received”.

2. Where a run starts — first files in order

You never open a test class first. The command (or Jenkins) wakes Maven. Maven reads pom.xml. That file decides the suite and the server.

1
You or Jenkins type a command

Example: mvn test -Pregression -Denv=staging. Default with only mvn test is smoke on the test server.

2
First project file: pom.xml

Picks the TestNG XML (smoke / sanity / regression / …) and passes -Denv into the tests. Java 21. Surefire runs TestNG.

3
Suite list: src/test/resources/testng-*.xml

Regression uses testng-regression.xml. It names the test classes and turns on the HTML report listener.

4
Server + data (loaded before any assert)

ConfigReader reads config.properties (test) or config-staging.properties (staging).
TestDataReader reads testdata.properties or testdata-staging.properties — QR code, item IDs, expected totals.

5
A test class runs

Example: InstructionTests. It asks QrTestHelper for a fresh session and a cart. That helper calls the API classes.

6
Checkout finish: CheckoutFlow.payAndConfirm

Telr browser → payment status → confirmation cart → OMS details. If OMS tokens are missing, checkout fails even if payment succeeded.

7
Report: ExtentReportListener

Writes reports/extent-report.html. Jenkins publishes that page. Console also prints the same business lines.

3. How the folders connect

Think of three layers: what the business expects, how we talk to Paytm, and the stories we run.

Settings Talk to the server Stories / checks
pom.xml and Jenkinsfile — the front door

pom.xml is the first file Maven reads. Jenkinsfile is the first file Jenkins reads. Jenkins only runs the same Maven command you run locally, plus Telr secrets and a copy of OMS tokens from the Jenkins machine.

src/test/resources — which restaurant and which numbers

config.properties / config-staging.properties = host URLs (QR site + OMS).
testdata.properties / testdata-staging.properties = QR code, item IDs, 20.00 cart, expected statuses.
testng-*.xml = which test classes belong to smoke, sanity, regression.
OMS token files are gitignored. Never commit them.

src/main/java/config — first Java used by every test

ConfigReader and TestDataReader load the files above. If env=staging, they switch files. No test hardcodes the live host.

src/main/java/api — one class per Paytm call

ApiRequestSpec sets base URL and JSON headers.
QrMenuApi opens the session.
CartApi adds items / reads confirmation.
PaymentApi starts Telr and later fetches status.
ApiCall retries if the server drops TLS (the Jenkins handshake flake).

src/main/java/pojo — shapes of request and response

These are field names the live API actually returns. We do not invent columns. Cart items are a positional table (not pretty JSON objects). OMS models live under pojo/response/oms.

src/test/java/tests — the stories

SmokeTests — session, 20.00 cart, Telr URL. No card pay.
SanityTests — account name, pending cart, customizable menu item.
NegativeTests — bad QR, empty cart, unknown item, bad payment link, short mobile.
CustomizationItemTests, CartVariantTests, CustomerDetailsTests, InstructionTests, RegressionTests — full Telr + OMS.
QrOrderFlowTest — long e2e only (-Pe2e).

src/test/java/tests/support — shared checkout

QrTestHelper builds the baseline cart and a fresh session. CheckoutFlow is the finish line: pay, confirm, read OMS. Every positive “create order” test goes through it so we do not stop at initiate_payment.

src/test/java/ui and config (secrets)

TelrHostedPage drives Chrome on Telr. TelrCardDetails and OmsCredentials read env vars or local gitignored files. OmsApi calls back-office order details.

4. What each suite is for

Product can read the left column. QA uses the command on the right.

Smoke

API only

Can we open the QR, build the 20.00 cart, and get a Telr link? Fast. No card. No OMS.

mvn test or -Psmoke

Negative

Must reject

Bad QR, unknown item, empty cart, broken payment link, short mobile. Expect HTTP 422 and a clear message.

mvn test -Pnegative

Sanity / Customization / Regression

Full checkout

Real Telr pay. Order must be accepted. OMS must match. Regression is the full pack (22 tests).

mvn test -Pregression -Denv=test

E2E

Full checkout

The long original flow class only. Same finish: Telr + OMS.

mvn test -Pe2e -Denv=test

Baseline basket (both servers): Kesar Pista Phirni quantity 2 (price 8) + Special Dates quantity 1 (price 4) = 20.00, tax 0.95, net 20.00, provider Telr. Item IDs differ by restaurant. Product names and money stay the same.

5. Two servers, same flow, different restaurants

The tests do not change. Only the settings file changes. Pick a tab.

Same on both: Telr cards, guest names, “No onions please” on Phirni only, size “2 pieces” = 9.00, biryani + dip = 48.00, OMS status success / method payment_gateway / type qsr.

6. What OMS must show after a paid order

Always

Same order id and order number as payment. Status order_accepted. Payment success. Method payment_gateway. Account / tenant id of that restaurant. Timeline accepted. Audit events payment_completed and order_accepted. Totals match the cart.

When the story needs it

Guest name on OMS (cart does not echo name). Item notes on Phirni only. Size name contains “2 pieces”. Add-on may collapse to one OMS line with customization text (example: Biryani Salan Dip). Cooking details are sent; OMS does not echo them — we do not fake a pass on that text.

7. How to run — laptop and Jenkins

On your laptop

mvn test — smoke, test server

mvn test -Pregression -Denv=test — testdeploy channel + OMS

mvn test -Pregression -Denv=staging — sprint205 + OMS

Need Chrome, Telr cards in env or telr.local.properties, and OMS tokens in the matching gitignored file.

On Jenkins (API-Deploy)

Open Build with Parameters.

SUITE = smoke / regression / …

ENV = test or staging

Telr comes from Jenkins Secret text. OMS comes from files on the Jenkins machine: ~/.jenkins/oms/test.properties and staging.properties. Do not put those in Git.
